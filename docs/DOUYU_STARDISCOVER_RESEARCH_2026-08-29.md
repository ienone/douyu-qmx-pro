# 斗鱼全民星推荐现网研究记录

> 整理日期：2026-08-29
> 研究发生于：2026-08-28 至 2026-08-29
> 来源：[共享研究对话](https://chatgpt.com/s/cx_6a91bf1097ac819197d7e9cf95aa0d04)、斗鱼现网页面与前端资源
> 说明：本文严格区分实测、静态分析和待验证项；接口可能随斗鱼更新而变化。

## 1. 结论摘要

- 新版页面仍保留星推荐红包入口、弹窗和领取按钮，现有红包 DOM 选择器仍能命中。“新版 UI 完全替换红包 DOM”不是当前不可用问题的主要解释。
- 旧调度每约 2 秒打开一个工作页，而红包组件约需 5.3～8.1 秒出现。标签很快进入后台后，页面定时器、渲染和懒加载更容易受浏览器节流影响，这更符合 Issue #52 中“手动激活后恢复”的现象。
- `square/list` 负责发现有红包的房间；`room/list` 返回指定房间的红包明细；领取使用 `snatch` POST。
- `square/list` 当前只提供 `rbId/rid/rbType/roomShowType/avatar`，没有奖池 `prizeList`；比较金币和星光棒数量仍需匿名查询候选房间的 `room/list`，但不需要打开直播页。
- `room/list.waitSec` 被前端当作“收到响应后再等待多久”，不是绝对剩余时间；前端按 `Date.now() / 1000 + waitSec` 建立倒计时，刷新页面会重新开始显示倒计时。
- 查询接口可匿名 GET，不要求登录 Cookie 或 `X-Requested-With`。领取接口需要登录态和动态 CSRF 字段。
- 提前调用 `snatch` 已完成现网验证：未到服务端时机时返回 `12006 / 稍等会儿才能抢哟`，到时后返回 `0 / success`。一次明确样本在本地相对倒计时仍剩 45 秒时已经成功，因此 API 状态必须优先于页面和本地预计倒计时。

## 2. 现网实测

### 2.1 活动房间与页面

研究时找到活动直播间 `12890459`，页面真实出现星推荐红包入口，并观察到：

| 字段 | 观察值 |
|------|--------|
| `rid` | `12890459` |
| `rbType` | `8` |
| `status` | `0` |
| `waitSec` | `300` |
| 页面状态 | 星推荐倒计时 |

不是每个直播间都是星推荐活动房间。普通直播间出现的其他活动入口不能用来验证星推荐逻辑。

### 2.2 加载耗时与后台标签

- 红包组件的前端初始化包含约 3 秒固定延迟，部分路径还会增加 0～3 秒随机延迟。
- 实测红包入口约在页面加载后 5.3～8.1 秒出现。
- 旧逻辑每约 2 秒打开下一个标签，前一个页面往往尚未完成组件挂载就进入后台。
- 后台标签受 Chromium 的计时器、渲染、冻结和资源调度策略影响。Windows 上现象可能更明显，但这不是 Windows 独有规则，不能假定 macOS 后台页一定可靠。

相关资料：

- [Chrome 后台标签策略](https://developer.chrome.com/blog/background_tabs)
- [Chrome 88 定时器节流](https://developer.chrome.com/blog/timer-throttling-in-chrome-88/)
- [Blink 任务调度](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/blink/renderer/platform/scheduler/TaskSchedulingInBlink.md)
- [Windows 窗口遮挡检测](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/docs/windows_native_window_occlusion_tracking.md)

因此，网络请求完成不等于红包 React 组件和 DOM 已经可用；只等 `load` 事件或固定短延迟不足以判断页面就绪。

## 3. 红包接口与前端流程

```text
square/list 发现活动房间
        ↓
room/list?rid=... 读取红包明细
        ↓
前端以响应到达时刻 + waitSec 建立倒计时
        ↓
倒计时结束后开放领取按钮
        ↓
snatch POST 领取
        ↓
读取 prizeList；领取记录由 snatch/record 类接口展示
```

### 3.1 查询接口

- `GET /japi/livebiznc/web/anchorstardiscover/redbag/square/list`
  - 用于发现当前有红包的直播间。
- `GET /japi/livebiznc/web/anchorstardiscover/redbag/room/list?rid=...`
  - 返回指定房间的红包列表。
  - `redBagList` 同时包含 `status=0` 的当前红包和 `status=3` 的历史红包。
  - `cnt` 是当前 `status=0` 的红包数，不是 `redBagList.length`。
  - 匿名 GET 已验证可返回数据。

现网只确认服务端返回过 `status=0` 和 `status=3`。前端代码中的 `-2/-1/4/10` 等值有些属于本地 UI 状态，不能直接当作服务端状态枚举。

### 3.2 倒计时

前端收到红包后采用等价于下面的计算：

```js
const endTime = Date.now() / 1000 + waitSec;
```

这说明：

- `waitSec` 是前端从本次响应开始使用的等待时长，不是可跨刷新复用的绝对剩余秒数。
- `createTime` 没有用于校准这段前端倒计时。
- 刷新后重新取得相同红包时，页面会重新开始一轮显示倒计时。

目前没有证据表明倒计时开始时会额外向服务器上传客户端当前时间；这项需要用新红包和网络日志再次验证。

### 3.3 领取接口与 CSRF

领取请求为：

```http
POST /japi/livebiznc/web/anchorstardiscover/redbag/snatch
Content-Type: application/x-www-form-urlencoded

code=...&id=...&rid=...&<动态CSRF字段名>=<对应Cookie值>
```

当前公共请求层不是固定生成 `ctn`，而是：

1. 从 `$SYS.tn` 读取 CSRF 表单字段名。
2. 从 `$SYS.cookie_pre + $SYS.tvk` 组合保存 token 的实际 Cookie 名。
3. 读取对应 Cookie；若不存在，先请求 `/wgapi/livenc/liveweb/csrfApi/getCsrfCookie`，再读取服务器设置的 Cookie。
4. 把动态字段和值并入表单。

2026-08-29 对新版直播页再次核对时，控制页内嵌配置解析为 `tn=ctn`、`tvk=ccn`、`cookie_pre=acf_`，实际 Cookie 名为 `acf_ccn`，且页面没有直接暴露 `window.$SYS`。另一个新版工作直播间的 42 个脚本中完全没有这些字段。当前实现因此由控制页共享动态字段映射给工作页，但不共享 Cookie 值或 token；工作页仍在每次请求前从当前登录会话读取 Cookie。实现只解析内嵌脚本，不保留旧的页面全局变量分支，也没有硬编码字段名。CSRF 证明请求来自合法登录会话，不能证明红包已经到领取时间。

`code` 当前只确认是 32 位十六进制字符串，没有证据确认其生成算法一定是 MD5。

## 4. 领取实验结果

已观察：

- 正常时间页面领取成功，得到金币 ×5、星光棒 ×5。
- 当前红包已领完时，页面会自动切到下一个红包。
- 修改本机时间会触发斗鱼“本机系统时间有误”提示，因此伪造本地时间不是有效验证路径。
- 新构建已安装到已登录的 Chrome/Tampermonkey，并完成真实同源 `snatch` 验证。
- 房间 `12865305` 的红包 `1663094` 首次返回 `waitSec=90`；按 5 秒轮询时，从本地预计剩余 90 秒到 50 秒均收到 `error=12006`、`msg=稍等会儿才能抢哟`。
- 同一红包在本地预计仍剩 45 秒时返回 `error=0`、`msg=success`，没有触发 DOM 兜底。
- 更新后的最新四个工作房间在统计时间线中均记录为 `API · 领取成功`；此前配置缺陷触发的 `DOM · 启用兼容领取` 仍保留在历史中，来源可区分。

仍未完成：

- 单个样本不能反推出服务端究竟按用户首次进入时间、统一活动时间还是其他状态计算资格；只能确认本地 `receivedAt + waitSec` 不是最终判定线。
- 因服务端在预计剩余 45 秒时已经成功，本轮没有进入最后 10 秒的 1 秒轮询区间；该切频逻辑目前由单元测试覆盖，尚缺现网触发样本。
- 活动配置显示每日红包额度为 50，但 `error=-1` 是否仍表示达到每日上限没有现网复测。

因此，当前可以确认 API 提前探测和直接领取可行，但不能据此确认服务端内部时钟模型，也不能把多次领取成功等同于长期账号安全验证。

## 5. 对插件升级的影响

### 5.1 兼容方案结论

后续阶梯实验确认：候选直播间在后台打开约 3 秒后关闭，控制页仍能在服务端开放时通过同一 `rid/id/code` 成功领取。因此不再需要长期保留工作页，DOM 弹窗点击兼容路径也已移除。

### 5.2 更小的目标流程

```text
API 找房间并比较奖池 → API 绑定红包 → 后台开页约 3 秒后关闭 → 控制页等待并轮询 snatch
```

当前实现只保留 `snatch` 领取路径。页面不再参与倒计时调度或模拟点击；页面短时打开只用于触发已实测存在的用户级初始化。

## 6. 下一次最小验证

1. 继续积累 `room/list` 首次接收时间、`waitSec/createTime`、首次 `snatch=0` 时间，比较多个红包的提前量是否稳定。
2. 继续观察每包最多 5 次的 `waitSec` 分段调度是否覆盖不同 5/10 分钟红包。
3. 刷新同一房间，对比新响应和倒计时，继续判断服务端是否保存用户级开始状态。
4. 到每日额度边界时记录脱敏响应，复核 `error=-1` 的当前含义。
5. 持续观察账号、请求频率和 API 直领成功率；功能成功不等同于账号安全结论。

账号封禁风险（Issue #59）尚未解决。任何改变领取路径或频率的实验都应使用最小请求次数，且不能把功能可用性测试当作账号安全验证。

## 7. 代码实施状态（2026-08-30）

- 已实现 `room/list` 红包查询、`rid/id/code` 单红包绑定和 `snatch` 同源 POST。
- 同一个红包只绑定 API 身份，不再根据 `waitSec` 或页面倒计时建立领取截止时间。
- 候选直播间在后台打开约 3 秒获取必要信息后关闭，不需要常驻；控制页按 `waitSec` 为每个红包最多安排 5 次 `snatch`，`12006` 保持等待，`0` 完成，`12001` 或 `status=3` 结束。
- DOM 弹窗点击、自动暂停视频、长期工作页心跳和兼容模式配置均已移除。
- 控制台日志和本地领取事件统一记录 `SNATCH` 来源，不记录红包 `code`、Cookie 或 CSRF token。
- 已在房间发现阶段有限并发查询候选 `room/list`，按活动红包的金币与星光棒奖池总量降序排列房间；奖池相同时优先等待时间更短的红包，失效候选剔除，查询失败候选降到已确认候选之后。
- 当前发布包只构建星推荐功能，弹幕助手暂不打包；用户只编辑控制室房间号，真实 RID 在保存时自动解析并作为隐藏映射保存。
- 统计页每次进入时主动刷新一次账户金币记录，手动刷新复用同一路径；星光棒继续来自本地成功领取事件。
- 旧版 5 秒/1 秒实现曾完成真实 `snatch` 验证；本次短时后台开页与新轮询调度已完成代码和自动化检查，仍需在登录态 Chrome 中做现网回归。
